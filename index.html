想先看看会改什么 Want to see what it would change first

TCPO_DRYRUN=1 tcpo

演练模式把所有写入路径重定向到一个临时目录，整条流程照跑、一个字节都不进 /etc，退出时把「将写入的文件」连内容一起打印出来。不需要 root —— 这正是它的用处：先在自己机器上看清，再决定要不要上生产机。 Dry-run mode redirects every write path into a temp directory: the whole flow runs, not a single byte reaches /etc, and on exit it prints every file it would have written, contents included. No root needed — that's the point: see it on your own box first, then decide whether to touch production.

它是靠重定向路径变量实现的，不是在每个写入函数里加判断 —— 所以写入函数一行都没改，也就不存在「某个分支忘了判断演练模式」这类漏洞：真实路径与演练路径跑的是同一份代码。改内核状态的动作（sysctl --system、tc、iptables、modprobe）另外单独跳过并打印被跳过的内容。 It works by redirecting the path variables, not by adding a check inside each writer — so the writers are untouched, and there's no "one branch forgot to check dry-run" class of bug: the real path and the dry-run path are the same code. Actions that change kernel state (sysctl --system, tc, iptables, modprobe) are skipped separately, printing what was skipped.

为什么要调 Why tune

Linux 默认网络参数是给局域网设计的，在高带宽高延迟的跨境链路上有两个瓶颈： Linux network defaults are designed for LANs. On high-bandwidth, high-latency cross-border links there are two bottlenecks:

  • 缓冲区太小：默认 rmem_max / wmem_max 只有 212KB。所需窗口 = 带宽 × RTT（BDP），1Gbps × 200ms ÷ 8 ≈ 25MB，默认值差两个数量级，链路跑不满。 Buffers too small: default rmem_max / wmem_max is only 212KB. Required window = bandwidth × RTT (BDP); 1Gbps × 200ms ÷ 8 ≈ 25MB. Two orders of magnitude short, so the link never fills.
  • Cubic 见丢包就砍速：跨境公网晚高峰 5% 以内的随机丢包是常态，Cubic 一遇丢包就把发送速率减半。BBR 改为实时测量链路真实容量与延迟，管道没满就继续发，不被随机丢包误导。 Cubic halves on any loss: a few percent of random loss is normal on cross-border links at peak hours, and Cubic halves its rate on every loss event. BBR measures actual capacity and latency instead, and isn't misled by random loss.

这两条不是推导，是实测的。test/effect-test.sh 用 netem 造出可控的长肥链路，在同一条链路上对比参数： These aren't derivations, they're measured. test/effect-test.sh builds a controlled long fat link with netem and compares settings on the same link:

BBR isn't "always 80× faster"; its value is not being misled by random loss. On a clean link the two are in the same league. The ranges are wide because absolute throughput inside a container depends on host load, so the tests only assert relative results within a single run.

缓冲区是怎么算的 How buffers are sized

按 BDP（带宽 × 延迟）算，不是拍内存百分比： From BDP (bandwidth × delay), not from a percentage of RAM: 

BDP(bytes) = 带宽MbpsMbps × 125 × RTT_ms
缓冲区上限buffer ceiling = BDP × 2.5，再受总内存 5% 约束，钳到 [8MB, 256MB], capped at 5% of total RAM, clamped to [8MB, 256MB]

RTT 由脚本 ping 三个公共地址取最小值实测（失败则按跨境典型值 150ms），带宽问你。按内存百分比算是代理指标：同一台 2G 内存的机器，跑 1Gbps/10ms 的同城线和 100Mbps/250ms 的跨境线，需要的窗口差 20 倍，但按内存算会得到同一个值。乘 2.5 是留给丢包重传期间的在途数据。 RTT is measured by pinging three public addresses and taking the minimum (falling back to a typical 150ms for cross-border links); bandwidth is asked. Sizing by RAM percentage is a proxy metric: on the same 2GB box, a 1Gbps/10ms local link and a 100Mbps/250ms cross-border link need windows 20× apart, yet RAM-based sizing gives both the same number. The 2.5× headroom covers data in flight during loss recovery.

可完整回退 Fully reversible

只做文件级、可完整回退的改动：sysctl drop-in、gai.conf、limits.d、/sys 队列设置、iptables 规则。判据是最坏情况必须停在「参数没生效」，不能是「用户重启后开不了机」——本面板经 SSH 使用，出事即失联无法自救。 Only file-level, fully reversible changes: sysctl drop-ins, gai.conf, limits.d, /sys queue settings, iptables rules. The rule is that the worst case must be "the setting didn't take effect", never "the box won't boot" — this panel is used over SSH, and a failure means losing access with no way to recover.

  • 先快照再改：菜单 2/3/4/5 任一入口都会先记录改动前的真实运行值，回退时逐个写回。快照读不到的 key 记为 ABSENT 并跳过，不用硬编码默认值兜底——机器原本可能就在跑 reno，发行版默认也可能是 fq_codel，猜错就是改成了另一个状态。 Snapshot before writing: menus 2/3/4/5 all record the actual running values first and write them back on rollback. Keys missing from the snapshot are marked ABSENT and skipped rather than filled with hardcoded defaults — the box may have been running reno, and the distro default may be fq_codel; guessing wrong means leaving it in a third state.
  • 删文件不等于回退：sysctl --system 只应用「文件里还写着的」值，对已删除的 key 不做任何事。所以回退是两步：删配置 + 跑 --system，再逐个写回快照值。中转档的 ip_forward=1 遗留意味着机器还在当路由器转包，回退最后会单独确认它。 Deleting the file is not a rollback: sysctl --system only applies values still present in files and does nothing for removed keys. So rollback is two steps: delete the configs and run --system, then write each snapshot value back. A leftover ip_forward=1 from the transit profile means the box is still routing packets, so rollback verifies that one explicitly at the end.
  • 冲突配置逐行注释，不禁用整个文件：发行版和加固包常把不相关的参数放在同一个 .conf 里，整文件移走会把无关的安全参数一起停掉。原文件先整份备份，清单落盘。 Conflicts are commented line by line, never by disabling whole files: distros and hardening packages often mix unrelated parameters into one .conf, and moving the file away would also disable unrelated security settings. The original is backed up in full and the list is recorded on disk.
  • 写进去不等于生效：被后加载文件覆盖、内核不支持该参数、模块没加载，三种情况都静默失败。菜单 3/4 跑完会逐项比对「配置文件写的」与「sysctl 实际读到的」，分三类报：已生效 / 不一致（红字）/ 本内核无此参数。 Written ≠ effective: being overridden by a later-loaded file, an unsupported parameter, or an unloaded module all fail silently. After menus 3/4, every key written is compared against what sysctl actually reads back, reported in three buckets: effective / mismatched (in red) / not supported by this kernel.
  • 生效不等于开机还生效：/etc/sysctl.d/ 是 systemd-sysctl 在开机时读的，没有 systemd 就没人读它，重启后全部回到原值。菜单 2/3/4 会先探测本机开机会不会重放，不会就如实说「本次已生效、开机不会自动重放」，并生成一个开机重放脚本（sysctl + BBR 模块 + 网卡队列一并重放）告诉你挂到哪。不自动改 wsl.conf 或 rc 目录——那会改变整个发行版的启动方式，超出「网络参数」范畴。WSL2 默认就不跑 systemd，是这条最常见的场合。 Effective ≠ effective after reboot: /etc/sysctl.d/ is read at boot by systemd-sysctl; with no systemd nobody reads it and everything reverts on restart. Menus 2/3/4 probe whether this box will replay at boot, and if not they say so plainly — "effective now, will not replay at boot" — and generate a boot replay script (sysctl + the BBR module + NIC queues in one) telling you where to hook it. They do not edit wsl.conf or rc directories for you: that changes how the whole distro boots, which is outside "network parameters". WSL2 runs without systemd by default and is where this comes up most.
  • 状态标记读真实生效值：主菜单的 BBR 与内核参数两项是三态——[已开启] 是配置在且实际在跑，[配置未生效] 是配置文件写着但当前运行值不符（无 systemd 的机器重启后就是这个状态），[未开启] 是压根没配过。只看「文件存在」会把第二种报成已开启，等于告诉用户一件没发生的事。 Status reflects live values: the BBR and kernel-parameter rows in the main menu are tri-state — [on] means configured and actually running, [config not effective] means the file says one thing and the running value says another (the normal state after rebooting a box without systemd), and [off] means never configured. Checking only "does the file exist" would report the second case as on, telling you something that didn't happen.

不做什么 Out of scope

  • 不换内核（XanMod BBRv3 / BBRplus / 锐速那类）。最坏情况是重启后开不了机，与「可完整回退」的性质冲突。要装请单独找专门的脚本，并确保不删旧内核、不自动重启。 No kernel replacement (XanMod BBRv3, BBRplus, and friends). The worst case there is a box that won't boot, which contradicts being fully reversible. Use a dedicated script for that, and make sure it keeps the old kernel and doesn't auto-reboot.
  • 不编译内核模块（tcp_brutal 之类只做检测提示），不集成隧道 / FEC。 No kernel module compilation (things like tcp_brutal are only detected and reported), no bundled tunnels or FEC.
  • 不做全能管理面板：SSH 加固、防火墙、swap、DNS、流媒体检测、跑分一律不加。 Not an all-in-one control panel: no SSH hardening, firewall, swap, DNS, streaming unlock checks, or benchmarks.
  • 每个参数都要有权威依据（内核文档 / 红帽 tuned / Cloudflare / ESnet 之一），社区脚本的流行度不构成依据。「故意不设」与「设了」同等重要——不设的参数在配置文件末尾注释区记录原因，防止后续版本当遗漏补上。 Every parameter needs an authoritative source (kernel docs, Red Hat tuned, Cloudflare, or ESnet); popularity among community scripts doesn't count. Deliberate omissions matter as much as what's set — skipped parameters are documented with reasons in a comment block at the end of the config file, so a later version doesn't "fix" them back in.

兼容性 Compatibility

Uses only POSIX tools and bash builtins; no GNU awk extensions (mawk is the Debian/Ubuntu default). The writing menus install what they need if missing (ping, ss, ethtool, iptables) across all six package managers — apt-get, dnf, yum, zypper, pacman, apk — and only degrade if that fails; the read-only menus install nothing on their own — the sole exception is iperf3, which generates real traffic and asks you first when menu a needs it.
